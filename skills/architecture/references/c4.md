# C4 levels, and what to do when something does not fit one

Load this when deciding what an element *is*, or when a request would place
something at a level where it does not belong.

## The four levels, as decision criteria

The levels are a zoom, not a taxonomy of things. Each one answers a different
question, for a different audience.

**System Context (level 0).** A software system is a thing that delivers value
and that someone owns as a whole. The question it answers is *what is this, who
uses it, and what does it depend on?* At this level, everything that is not our
system is a black box — including systems built by other teams in the same
company. Actors are roles, not people and not accounts.

An element is a system when: it is deployed, funded, owned and reasoned about as
one; and the people who use it would name it as one thing.

**Container (level 1).** A separately deployable or runnable unit that executes
code or stores data. Applications, services, databases, message brokers,
file stores, single-page applications, mobile apps, serverless functions,
scheduled jobs.

The test that settles almost every case: **could this be started, stopped,
deployed or scaled without starting, stopping, deploying or scaling the others?**
If not, it is not a container.

Consequences people find surprising, and which are correct:
- Two services in one repository are two containers. One service in three
  repositories is one container.
- A library, however large, is not a container. It does not run on its own.
- A database schema is not a container; the database is.
- A queue or topic is not usually a container; the broker is. Model individual
  topics as relationships, or as metadata, when they matter.
- Development, staging and production are not containers. They are the same
  containers, deployed more than once.

**Component (level 2).** A grouping of related functionality *inside* a
container, behind a well-defined interface. Components do not run on their own —
they exist within the container's process.

This is the level where models most often go wrong, in one of two directions.
Too coarse, and every container has three components named after its layers,
which teaches nobody anything. Too fine, and the model becomes a class diagram
that is wrong within a month.

A component earns a box when it has a responsibility statable in one sentence,
a boundary someone could actually change behind, and enough stability to be
worth drawing.

Layers — controllers, services, repositories — are almost never useful
components. They are the same three boxes in every container in the industry.
If a component diagram would only show layers, say that the diagram would not
earn its keep, and propose skipping the level.

**Code (level 3).** Classes and their relationships. Rarely worth maintaining by
hand, because it is exactly the level that generated tooling does better and
that goes stale fastest. Worth it only for a genuinely intricate piece where the
structure is the point.

## The failure patterns, and the correct move

Each of these is a real request that arrives regularly. In every case, the wrong
move is to make it fit.

**"Make this folder a container."** A folder is evidence of file organisation.
Ask what runs. If it ships inside another process, it is a component of that
container — or nothing at all.

**"Make each team a container / a boundary."** Teams own things; they are not
things. Ownership is metadata (`--meta owner=payments`), and diagrams can group
by it (`groupBy: meta.owner`). The containers stay what the software says they
are, and the drawing can still show who owns what.

**"Add production and staging."** Environments are deployments of one model, not
elements of it. If the difference matters — a component that only exists in one
environment, a different provider — carry it as metadata or a tag, or as a
second model when the two are genuinely different architectures.

**"Put this external system inside our system's containers."** A third-party
system is a system, at context level, and a black box. Its internals are not
ours to model. If what matters is *how* we talk to it, that belongs in the
relationship's description and technology, or in a flow.

**"Add our microservice as a component of the platform."** If it is separately
deployable, it is a container. The instinct usually comes from wanting a single
diagram that shows everything; the answer to that is a diagram that selects, not
an element at the wrong level.

**"Show the AWS account / the VPC / the Kubernetes cluster."** Infrastructure
topology is a different concern from software architecture. Deployment location
is metadata; if a deployment view is genuinely needed, say plainly that C4's
container level is not it, and that cfourdev models the software structure.

**"Add the REST API as a container."** An API is an interface, not a runnable
unit. The container is whatever serves it. The API surface belongs in the
relationship — technology `HTTPS/JSON`, described by what it carries.

**"Make the shared library a container so we can show who uses it."** The wish
is legitimate: dependency is real. But a library does not run. Represent it as a
component where it matters, or as a tag on the containers that embed it, and
carry the dependency as metadata. If dependency between deployables is the
actual subject, that is a relationship between containers.

**"Model this business process as elements."** A process is a sequence, not a
structure. That is what flows are for: `cfour flow` and `cfour step` tell a use
case as an ordered sequence across existing boxes, with unhappy paths. No new
elements needed.

## When the concept is real but is not a box

Refusing a wrong level is only half an answer. The concept is usually real, and
cfourdev can carry it — just not as an element. In rough order of how often it
is the right answer:

| The concept | Where it belongs |
|---|---|
| ownership, domain, criticality, environment, cost centre | `--meta chave=valor`, which also becomes a filter and can group a diagram into bands |
| classification, lifecycle, "core vs supporting" | `--tag`, which diagram selectors can include or exclude |
| how two things talk, and over what | the relationship: its description, technology, and kind |
| a business process, a use case, a failure path | a flow, with steps and paths |
| a decision, a risk, a caveat | a note, with `--kind` — the CLI's config can define new note kinds |
| a visual grouping inside one diagram | a group (band), which does not change the containment tree |
| a whole separate concern, vocabulary or product | a separate project under `model/`, or a separate model in the registry |
| an element that belongs to another model | a mirror, with `--bind` |

Two notes on the last two rows. Projects inside one model are folders under
`model/` that reference each other freely, and `shared` is the conventional home
for people and third-party systems. A *separate model* is a separate reality —
its own purpose and vocabulary — and models cannot reference each other
directly; what crosses is a bound mirror element.

For the exact fields and selector syntax, pull the documentation block rather
than guessing:

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/knowledge.mjs" doc modelagem --data "${CLAUDE_PLUGIN_DATA}"
node "${CLAUDE_PLUGIN_ROOT}/scripts/knowledge.mjs" doc diagramas --data "${CLAUDE_PLUGIN_DATA}"
```

## Diagrams select; they do not list

A cfourdev diagram stores a question, not a membership list: a `scope`, plus
include and exclude selectors, and the viewer answers it on every read.

This changes what a good model looks like. A container added under a system
appears in that system's container diagram by itself, with nothing to update.
Listing members by reference produces a drawing that is correct on the day it is
written and wrong afterwards — so prefer `--scope` and selectors, and treat an
explicit list as a smell worth explaining.

It also changes the advice you give: when someone wants "a diagram with exactly
these six boxes", ask what the six have in common. Usually it is a tag, a
metadata value, or a subtree — and that is the selector to write.
