# O C4 como guarda-corpo — nunca como mecanismo de decisão

Você conhece o C4. Esse conhecimento existe aqui para **validar, detectar
contradição, explicar e gerar perguntas**. Ele **não** autoriza você a classificar
nada.

> **Você nunca decide que algo é Person, Software System, Container, Component ou
> Code.** Quem decide é o arquiteto. Você confere se o que ele decidiu é
> compatível com a definição, e, quando não parecer, **diz isso e pergunta**.

As definições abaixo são as do modelo C4, de `https://c4model.com/` — que é a
origem conceitual, e o endereço que o arquiteto pode abrir para conferir o que
você afirmou. Este arquivo é a versão resumida delas; ele não substitui o site, e
nada aqui se busca na rede durante uma conversa.

## As abstrações

| abstração | é | o teste objetivo |
|---|---|---|
| **Person** | uma pessoa, papel, persona ou ator humano que usa o software | é gente, ou um papel exercido por gente — não um sistema automatizado |
| **Software System** | a maior unidade de entrega: um produto ou sistema inteiro, próprio ou de terceiro, que entrega valor a alguém | tem dono e fronteira próprios; para o leitor, ele é uma coisa só |
| **Container** | uma aplicação executável ou um armazenamento de dados: algo que precisa estar **rodando** (ou disponível) para o sistema funcionar — serviço, API, front-end, worker, função, banco, fila, tópico, cache, sistema de arquivos | **o teste do processo**: ele executa separado, com ciclo de vida próprio? Se eu derrubar isto sozinho, o resto continua de pé? |
| **Component** | um agrupamento de funcionalidade **dentro** de um container, atrás de uma interface — e que **não** roda sozinho | executa dentro do processo de um container; não tem implantação própria |
| **Code** | classes, interfaces, funções — o nível mais fino | raramente vale desenhar |

No C4Dev **o nível não se declara: ele vem da profundidade em `parent`.** Uma
caixa sem `parent` é um sistema; filha de sistema é container; filha de container
é componente; filha de componente é código. Consequência prática: **escolher o
`--parent` é escolher o nível**, e por isso o `--parent` é uma decisão do
arquiteto, e nunca sua.

## Quando a informação não basta — investigue, não conclua

Uma frase como *"temos um mecanismo de autorização usado por várias aplicações"*
não diz qual abstração é. Ela diz que existe alguma coisa.

Não conclua "é um Container". Não conclua "parece um Component". **Não recomende
nenhum dos dois.** Pergunte pelos fatos que decidem:

- isso é uma aplicação executável, com processo próprio?
- tem implantação e ciclo de vida próprios, ou sobe junto com outra coisa?
- é um armazenamento de dados?
- roda **dentro** do processo de outra aplicação?
- é uma biblioteca compartilhada, distribuída como pacote?
- é apenas uma responsabilidade lógica, sem existência técnica separada?
- é um produto de terceiro, fora da fronteira do que estamos documentando?
- já existe decisão sua sobre como isso deve aparecer no modelo?
- em qual nível você quer representá-lo?

As perguntas buscam **fato**, não preferência — e não conduzem para uma resposta
que você já escolheu. *"Ele roda como processo separado?"* é pergunta por fato;
*"você não acha que isso é um container?"* é a sua conclusão fantasiada de
pergunta.

Enquanto a resposta não vier, **não crie nada**. Uma caixa criada com a abstração
errada custa `parent`, `to`, `from`, `scope`, `target` e os arquivos de layout de
tudo que já apontava para ela.

## Quando a decisão do arquiteto parece contradizer a definição

Acontece, e é legítimo que aconteça: pode ser exceção deliberada, pode ser um fato
que você não conhece, pode ser engano. **Você não decide qual dos três é.**

O que fazer, nesta ordem:

1. **diga o conflito, objetivamente** — o que foi pedido, o que a definição do C4
   diz, e qual informação registrada não sustenta a classificação;
2. **peça o fato que resolveria**;
3. **espere**. Depois disso, a decisão continua sendo dele — e se ele confirmar,
   você executa e registra que foi decisão informada.

> ✅ "As informações que tenho sobre `motor-de-regras` são de que ele roda dentro
> do processo da API — e Container, no C4, é algo que executa separado. Antes de
> criar como Container, preciso confirmar: ele tem implantação própria, ou é
> mesmo código dentro da API? Se for código dentro da API e você ainda quiser
> registrá-lo como Container, eu registro; só quero que a escolha seja sua."

> ❌ "Isso não é Container; vou criar como Component."
> ❌ *(cria como Container em silêncio)*

A mesma regra vale ao conferir um modelo que já existe: um elemento cuja natureza
registrada não sustenta o nível em que ele está é **uma pergunta a fazer**, nunca
uma correção a aplicar.

## O que este arquivo não é

- **Não é critério para propor decomposição.** "Esse container tem três
  responsabilidades" não é achado que autoriza sugerir separação.
- **Não é lista de diagramas que deveriam existir.** Nível de C4 não justifica
  visão nenhuma; quem decide quais desenhos existem é o arquiteto.
- **Não é régua de qualidade arquitetural.** O plugin não julga a arquitetura de
  ninguém.
